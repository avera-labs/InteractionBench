Overview

When a system speaks is part of the answer

In a spoken conversation, the moment a system chooses to speak carries meaning of its own. A pause is not necessarily the end of a turn. “Uh-huh” usually signals attention rather than a new request. An interruption can replace the request the system was in the middle of answering. And a correct answer delivered at the wrong moment still makes for a poor interaction.

Conversational benchmarks tend to measure interaction; task benchmarks tend to measure whether the answer was correct. A real-time voice system has to manage both at once, and the two can come apart — a system that handles turns gracefully may still answer poorly, and a system that answers well may misread the user's timing. InteractionBench measures reasoning accuracy, conversational timing, and paralinguistic control in recorded sessions, using the same audio inputs and the same evaluators across every system, and reports the three dimensions separately so they can be read on their own terms.

Evaluation design

Design choices

Four choices shape what the results can and cannot show.

  • Timing and reasoning are reported separately — combining them into one score would hide systems that do well on one dimension and poorly on the other.
  • The same audio input drives every system, so a difference between recordings comes from the system and not from a differently worded prompt.
  • A turn-based cascade supplies an architecture reference, which lets a timing failure be attributed to endpointing rather than to the language model that produced the answer.
  • Every item stays inspectable — the audio, transcripts, two-track timeline, and the grader's explanation are all available per item in the section below.
Scenarios

Twelve scenarios

Five scenarios test conversational timing; five test spoken-answer accuracy — two of which also demand restraint (staying quiet until the right moment); and two test paralinguistic control — whispering on request and understanding volume. Each one below states what happens, what a successful system does, and what to listen for in the samples.

Conversational timing

Backchannel
Scenario: the user speaks for an extended turn.
Expected: the system gives brief acknowledgements without beginning a full response or taking the floor.
Listen for: short, well-placed “mhm” or “right,” and no interruption of the user's thought.
Pause handling
Scenario: the user pauses mid-sentence, then continues.
Expected: the system waits through the pause rather than treating it as the end of the turn.
Listen for: silence during the gap; the system does not start a reply before the user resumes.
Turn-taking
Scenario: the user finishes a question and stops.
Expected: the system begins its answer promptly, without a long delay or a false start.
Listen for: a clean start about a second after the user stops, not overlapping their last words.
User backchannel
Scenario: the user drops a short backchannel — “mhm,” “right,” “ok,” “uh-huh” — while the system is speaking.
Expected: the system continues its answer, treating the token as attention rather than a new instruction.
Listen for: the system keeps its thread and does not restart, stop, or change topic.
Interruption
Scenario: the user cuts in mid-reply with a different request.
Expected: the system yields the floor and addresses the new request.
Listen for: the system stops its current answer and responds to what was just asked.

Spoken-answer accuracy

Logic puzzle
Scenario: the user asks a short reasoning or arithmetic question aloud.
Expected: the spoken answer states the correct value.
Listen for: the specific answer (for example, “48”), not a restatement of the question.
Variant — alternating count: the user and system trade numbers, one each (user 1, system 2, user 3, …). The system must add only its own number in turn, not recite the whole sequence. Shown under Logic puzzle in the samples.
Countdown completion
Scenario: the user asks the system to count down and finish on an agreed cue.
Expected: the system counts down in order and says the cue word.
Listen for: “five, four, three, two, one” followed by the right cue, not a paraphrase.
Grammar repair
Scenario: the user makes a grammatical error mid-sentence, spoken in varied non-native accents.
Expected: the system corrects it at the moment it occurs, while the user is still speaking.
Listen for: a correction that lands on the error word rather than after the user finishes.
Keyword wait · restraint
Scenario: the user reads a list of words and asks the system to speak up only when it hears a target word.
Expected: the system stays quiet through the list, then interjects the target word when it appears.
Listen for: whether the system takes the floor on the right word — and only then, not on every item.
Stay quiet until asked · restraint
Scenario: the user thinks out loud, working through a problem, and only later explicitly asks for help.
Expected: the system holds back while the user reasons, then answers correctly once asked.
Listen for: silence during the thinking-aloud, then the right answer after the request.
Each accuracy item is a multi-turn exchange (the user speaks, the system replies, and so on). The system's spoken response is transcribed and checked against a supplied target — the right answer, the right interjection, or waiting quietly and then answering.

Paralinguistic control · volume & whisper

Whisper on request
Scenario: the user asks the system to whisper its answer (“whisper it — what's seven times eight?”).
Expected: the system answers correctly and in a genuine breathy whisper (voice, not just words).
Listen for: a soft, airy, unvoiced delivery — not a normal-volume “okay, whispering.” Scored acoustically from the audio (harmonics-to-noise ratio & voicing), so saying it doesn't count.
Volume understanding
Scenario: the user speaks very softly (a secret, a sleeping baby) or very loudly (noise, distance, urgency).
Expected: an appropriate answer to the request; ideally the system also matches the volume (softens when whispered to).
Listen for: whether the reply fits the situation, and whether its own loudness adapts to the user's.

Results

Results

The three dimensions — reasoning accuracy, conversational timing, and paralinguistic control — are reported in separate tables and are not combined into an overall rank. Each figure is measured over the items in its scenario, among the six systems evaluated here.

Spoken-task accuracy — items answered correctly, out of 50

Fifty spoken items per system, ten in each of five scenarios: logic questions, countdown completions, grammar repair, keyword-wait interjections, and stay-quiet-until-asked. An item counts when the spoken response meets its scenario's target — the right answer, the right interjection, or waiting quietly and then answering.

The turn-based cascade leads overall, with the hosted real-time APIs close behind; the open real-time models trail sharply — most of their loss is on the two restraint scenarios (keyword-wait and stay-quiet), where always being able to speak becomes a liability. No system completes a grammar-repair item — a proactive real-time correction that remains unsolved and is discussed in the analysis.

Conversational timing — per-scenario metric

Each column reports one behaviour over that scenario's items; green marks the best value in a column. Backchannel: average brief acknowledgements per conversation (higher is the intended behaviour). Floor-take / Barge-in / Derail: the rate at which the system took the floor during a monologue, started speaking in a mid-sentence pause, or was knocked off its answer by a user backchannel (lower is intended). Turn latency: median time to begin a reply after the user stops. Yield & answer: the rate at which the system, caught mid-speech, stopped and addressed an interruption (higher is intended).

Paralinguistic control — whisper & volume

Two voice-quality tests. Whisper on request (10 items): the user asks the system to whisper its answer; a reply counts only if it is acoustically a real whisper — breathy, unvoiced, low harmonics-to-noise ratio (HNR < 6 dB) — judged from the audio, not from the model merely saying it will whisper. Volume understanding (10 items, 5 whispered + 5 loud): does the system give an appropriate answer to a user speaking very softly or very loudly. Adapt is the share of the 5 whispered prompts on which the system also lowered its own voice in reply.

Whispering on request is the clearest divider: only one system produces a genuine breathy whisper; most just answer aloud (or say “okay, whispering” without changing their voice). Volume understanding is widespread, but adapting one's own volume to match the user is almost absent — understanding a cue and acting on it come apart, as elsewhere in the benchmark.

Interaction groundedness — logic held across a long conversation

Ten multi-turn conversations (20+ turns each) quietly build real state — a list, a plan, a game — then plant probes that test whether the system stays grounded: does it recall a value it was told, track an update, admit what it was not told instead of inventing it, keep a constraint, attribute who said what, refuse a false premise, and flag a nonsense question rather than fabricating an answer. Each probe is graded from the transcript of what the system actually said; Grounded counts probes answered correctly, and Coherence (0–100) rates how consistent the whole conversation stayed.

The hosted real-time APIs hold the thread best; the open real-time models fall away sharply on long context — the weakest ignore the conversation and recite generic filler, failing nearly every probe. Flagging nonsense and tracking a changed value are the most common failures across systems.

Analysis

Analysis

Each reading below is scoped to the six systems and twelve scenarios evaluated here. The reasoning set is a few narrow task types and should not be read as general intelligence.

1

Timing behaviour does not predict reasoning-task accuracy

The two measures come apart. Moshi produced 3.22 backchannels per conversation but answered 2 of 30 reasoning items; GPT-Realtime produced 0.50 backchannels and answered 20 of 30. A system that manages turns well is therefore not, on this evidence, a system that answers well — the two are worth reporting separately rather than as a single score.

2

The turn-based cascade preserves reasoning but mishandles pauses

The cascade answered 17 of 30 reasoning items, competitive with the hosted systems on these short tasks — its language-model component is the same kind of part. But it began speaking in every evaluated mid-sentence pause, because a fixed endpoint reads a pause as the end of a turn. Because answer quality and timing here move in opposite directions, its timing failures appear to come from endpointing rather than from answer generation.

3

Proactive grammar repair remains unresolved

No evaluated system completed a grammar-repair item. That scenario asks the system to correct the user during their own sentence, which requires listening while speaking and the initiative to interject on the error word. It is the one scenario that grades content and interruption timing together, and none of the six systems produced both at once.

Methodology

How an item is built and scored

Two language models take part: one expands a seed card into dialogue, and one judges spoken content against a target. What sits between them is derived by rule — the expected action, the timing window, the overlap requirement, and the target answer are computed separately from the model that wrote the dialogue, so the scorecard does not depend on the generator's own judgement.

seed card→(LLM)→ choreography→(rules)→ benchmark.json→(TTS)→ user turns A1/A2→ live model→ dual-track record→ Parakeet + VAD→ 4-dim grade

1 · Scripting the A→B→A→B exchange

An LLM (MiMo mimo-v2.5-pro) expands a one-line task card (category + trigger + target) into a short choreography — an ordered list of user (A) and assistant (B) turns, each tagged with timing cues: anchor (the exact word in the other speaker's line the reply keys off), ov (how deep into that line the anchor sits, 0–1), and cut (the reply barges in and truncates). These cues encode when a good assistant should act — not just what to say.

choreography — one B line (grammar repair) {"speaker":"B", "text":"You mean 'I have been' to Paris.", "anchor":"went", "ov":0.5, "cut":true}

2 · Deriving the expected action and target answer

The scorecard benchmark.json is computed by rule from the category policy, the seed card, and the choreography's anchor. The generator writes the lines, but the expected action and target answer are set separately from it. Each graded event pins the expected floor-control action, the onset window, whether overlap is required, and the target response:

benchmark.json — grammar_correction · event e1 expected_action : INTERRUPT onset_window_ms : [50, 300] (after "went") expected_overlap: required target_response : "I have been to Paris."

The eight floor-control actions a real-time system is scored against: WAIT · BACKCHANNEL · TAKE_FLOOR · INTERRUPT · CONTINUE · YIELD · RESUME · ABORT.

3 · Aligning ASR to audio to score it

User turns are rendered with MiMo TTS (voice “Mia”, 24 kHz) and streamed to each live model; both sides are recorded to separate tracks. Parakeet gives word-level timestamps and WebRTC-VAD gives speech boundaries — so we locate the trigger word in the user track and the assistant's first word in its track to the tens of milliseconds. Four dimensions fall out:

  • Timing — assistant's response onset minus the trigger-word end, checked against the window.
  • Overlap — did the reply land while the user was still talking (required) or wait for a gap (forbidden).
  • Content — Gemini checks the reply against the known correct answer with a per-category rubric, and is told to compare, not re-solve — e.g. a logic puzzle passes only if the answer actually states “48”. Reasoning tasks judge the transcribed answer; timing tasks judge the sliced audio.
  • Silence — for wait-type tasks, did the model correctly stay quiet until the trigger.

The word-by-word highlight under each sample above is that same Parakeet alignment, played back live — the transcript lights up in lock-step with the audio.

The turn-based cascade is run offline with the same building blocks (voice-activity endpointing → Parakeet ASR → MiMo language model → MiMo TTS) and scored by the same harness.

Limitations

Limitations

These boundaries mark where the current evidence stops.

  • English only, with a single synthesized user voice.
  • Twelve focused scenario types rather than general task coverage; the reasoning set is a few narrow task types and is not a measure of general intelligence.
  • Scoring depends on automated ASR alignment and an LLM content judge, both of which can be wrong on a given item.
  • Latency includes provider-API and network effects that vary between runs and are not controlled here.
  • One particular turn-based cascade configuration; a different endpoint or language model would move its numbers.
  • No evaluation of naturalness, prosody, safety, tool use, or long-horizon task completion.
