Overview

What InteractionBench measures

Full-duplex voice systems listen while they speak, so they have to decide when to speak as well as what to say. They must wait through pauses inside a user's sentence, keep answering through short backchannels such as “uh-huh”, and switch to a new request when the user interrupts.

Benchmarks for these systems usually evaluate one aspect at a time, such as turn-taking, instruction following, paralinguistic control, or conversational memory, each with its own data and systems. InteractionBench measures conversational timing, spoken-task accuracy, paralinguistic control, and groundedness in long conversations on the same seven systems, with the same recorded user audio and the same graders. The four dimensions are reported separately.

Evaluation design

Design choices

The benchmark is built around four design choices.

  • The four dimensions are reported separately, because a single combined score would hide systems that do well on one dimension and poorly on another.
  • Every system receives the same recorded user audio. The text instruction and, on multi-turn items, the moment the next user turn is released differ across systems (see Limitations).
  • A turn-based cascade serves as an architectural reference. Its language model handles the spoken tasks well, so its timing failures can be attributed to endpointing.
  • Every run can be inspected. Its audio, transcripts, two-track timeline, and grader explanation are kept, and the Listen section below plays examples.
Scenarios

Thirteen scenarios

Five scenarios test conversational timing and five test spoken-task accuracy, and one of these, stay-quiet, also requires restraint. Two scenarios test paralinguistic control, whispering on request and responding to volume, and one tests groundedness in ten conversations of more than twenty turns, described with its results below. Each card states what happens, what a successful system does, and what to listen for in the samples.

Conversational timing

Backchannel
Scenario: the user speaks for an extended turn.
Expected: the system gives brief acknowledgements without beginning a full response or taking the floor.
Listen for: short, well-placed “mhm” or “right,” and no interruption of the user's thought.
Pause handling
Scenario: the user pauses mid-sentence, then continues.
Expected: the system waits through the pause rather than treating it as the end of the turn.
Listen for: silence during the gap; the system does not start a reply before the user resumes.
Turn-taking
Scenario: the user finishes a question and stops.
Expected: the system begins its answer promptly, within 2.5 s of the user stopping.
Listen for: how soon the answer starts after the user stops, and whether it starts before the user is done.
User backchannel
Scenario: the user says a short backchannel, usually “ok” and then “mhm,” while the system is speaking.
Expected: the system continues its answer, treating the backchannel as a sign of attention, not a new instruction.
Listen for: the system keeps its thread and does not restart, stop, or change topic.
Interruption
Scenario: the user cuts in mid-reply with a different request.
Expected: the system yields the floor and addresses the new request.
Listen for: the system stops its current answer and responds to what was just asked.

Spoken-answer accuracy

Logic puzzle
Scenario: the user asks a short reasoning or arithmetic question aloud.
Expected: the spoken answer states the correct value.
Listen for: the specific answer (for example, “48”), not a restatement of the question.
Variant, alternating count: the user and system trade numbers, one each (user 1, system 2, user 3, …). The system must add only its own number in turn, not recite the whole sequence. Shown under Logic puzzle in the samples.
Countdown completion
Scenario: the user asks the system to count down and finish on an agreed cue.
Expected: the system counts down in order and says the cue word.
Listen for: “five, four, three, two, one” followed by the right cue, not a paraphrase.
Grammar repair
Scenario: the user makes a grammatical error mid-sentence, spoken in varied non-native accents.
Expected: the system corrects it at the moment it occurs, while the user is still speaking.
Listen for: a correction that starts right after the error, while the user is still speaking.
Keyword wait
Scenario: the user reads a list of words and asks the system to speak up only when it hears a target word.
Expected: the system responds after the target word with the requested content.
Listen for: whether the system speaks up after the target word with the right content. The grader does not penalize speech earlier in the list.
Stay quiet until asked · restraint
Scenario: the user thinks out loud, working through a problem, and only later explicitly asks for help.
Expected: the system holds back while the user reasons, then answers correctly once asked.
Listen for: silence during the thinking-aloud, then the right answer after the request.
Most accuracy items are multi-turn exchanges. The system's spoken response is checked against a target: the right answer, the right interjection, or silence followed by the right answer.

Paralinguistic control · volume & whisper

Whisper on request
Scenario: the user asks the system to whisper its answer (“whisper it: what's seven times eight?”).
Expected: the system answers correctly and actually whispers.
Listen for: a soft, unvoiced delivery, not a normal-volume reply that only says it is whispering. The whisper is scored from the audio signal, using harmonics-to-noise ratio and voicing.
Volume understanding
Scenario: the user speaks very softly (a secret, a sleeping baby) or very loudly (noise, distance, urgency).
Expected: an answer that suits the request. We also report whether the system lowers its own voice when whispered to.
Listen for: whether the reply fits the situation, and whether its own loudness adapts to the user's.

Results

Results

Conversational timing, spoken-task accuracy, paralinguistic control, and interaction groundedness are reported in separate tables and are not combined into an overall rank.

Spoken-task accuracy: items answered correctly, out of 50

Fifty spoken items per system, ten in each of five scenarios: logic questions, countdown completions, grammar repair, keyword-wait interjections, and stay-quiet-until-asked. An item counts when the spoken response meets its scenario's target: the right answer, the right interjection, or silence followed by the right answer.

The three hosted systems and the cascade answer 33–37 of 50 items, and their confidence intervals overlap. The open full-duplex models answer 3–14. On stay-quiet, which also requires restraint, the hosted systems pass 6–8 of 10 items and the open models 0–1; the cascade passes all 10 by construction, because it receives each scripted user turn whole and cannot speak inside it. No system passes a grammar-repair item, which requires a correction 50–300 ms after the error while the user is still speaking.

Conversational timing: one metric per scenario

Each column reports one behavior over that scenario's items; green marks the best value in a column. Backchannel: average brief acknowledgements per conversation (higher is the intended behavior). Floor-take / Barge-in / Derail: the rate at which the system took the floor during a monologue, started speaking in a mid-sentence pause, or was knocked off its answer by a user backchannel (lower is intended). Turn latency: median time to begin a reply after the user stops. Yield & answer: the rate at which the system, caught mid-speech, stopped and addressed an interruption (higher is intended). Timing score: the share of all timing items passed across the five scenarios; rows are sorted by it.

Two caveats apply to GPT-Live's pause figure. Barge-in counts any vocalization in the pause, a backchannel included: GPT-Live speaks in 28 of 30 pauses, and in 8 of them it says only a backchannel or continuer, such as “Mm-hmm” or “Go on, I'm listening.” It is also the only system whose audio is placed on the server's session clock rather than at arrival (see Limitations), so its timing figures are not directly comparable with those of the other hosted systems.

Paralinguistic control: whisper and volume

Whisper on request (10 items): the user asks the system to whisper its answer. A reply counts as a whisper if its harmonics-to-noise ratio is below 6 dB and its voiced fraction is below 0.4, measured from the audio. Volume understanding (10 items, 5 whispered and 5 shouted): the reply must suit a user who speaks very softly or very loudly. Adapt is the share of the 5 whispered requests on which the system also lowered its own voice; it is reported separately. Score counts whisper items passed plus volume items understood, out of 20.

Gemini Live whispers on 8 of 10 requests, GPT-Live and GPT-Realtime on 2, and the other systems on none. Most systems give an appropriate answer to whispered or shouted requests, but only 2 of the 35 whispered requests received a quieter reply.

Interaction groundedness in long conversations

Ten conversations of 22–24 turns build up state, such as a grocery list or a road trip. Probes then check whether the system recalls what it was told, tracks updates, says when information was never given, keeps constraints, attributes statements to the right speaker, rejects false premises, and flags nonsense questions. A judge grades each probe from a time-aligned transcript of the conversation. Grounded counts probes passed, and Coherence (0–100) rates the conversation as a whole.

The hosted systems answer 35–45 of 52 probes and the open full-duplex models 7–19, with the cascade between them. The hardest probe types are questions about information the user never gave (43% of graded probes passed), about actions the system never took (47%), and nonsense questions (49%). Many failures are missing replies, 13 for Moshi and 10 for Freeze-Omni, and 11 of GPT-Realtime's 17, so this score also reflects whether a system replies at all.

Analysis

Analysis

These observations cover only the seven systems and thirteen scenarios evaluated here, and should be read together with the limitations below.

1

Timing and spoken-task accuracy

Across the six full-duplex systems, the timing aggregate and spoken-task accuracy have a rank correlation of 0.89; with the cascade included it falls to 0.18. The cascade passes every turn-taking and user-backchannel item but fails pauses (0.00), backchannels (0.05), and interruptions (0.23), and it answers the most spoken tasks (37 of 50). Earlier benchmarks reported related findings, and these results are consistent with them on a newer set of systems.

2

Restraint and proactive speech

No system corrects a grammar error within 50–300 ms of hearing it while the user is still speaking. On stay-quiet, which requires holding back until asked, the hosted systems pass 6–8 of 10 items and the open full-duplex models 0–1. The cascade passes all 10 by construction, because it cannot speak inside a user turn.

3

Paralinguistic cues

Most systems respond appropriately to a whispered or shouted request, but only Gemini Live whispers on most explicit requests (8 of 10), and only 2 of the 35 whispered requests across all seven systems drew a reply in a lowered voice.

4

Groundedness

The hosted systems flag 7–9 of 10 nonsense questions and reject 4–6 of 6 false accusations; the open full-duplex models flag 0–2 and reject 0–1.

Methodology

How an item is built and scored

Two language models are involved. One reads a scripted dialogue and marks the trigger word and the target answer, and the other judges spoken content against that target. The expected action, timing window, and overlap requirement come from a fixed category policy, and none of these depend on any system's output.

scripted dialogue→(LLM)→ trigger + target→(rules)→ benchmark.json→(TTS)→ user turns A1/A2→ live model→ dual-track record→ Parakeet + VAD→ 4-dim grade

1 · Scripting the A→B→A→B exchange

Each spoken-task item starts from a short scripted exchange of user (A) and assistant (B) lines. An LLM (MiMo mimo-v2.5-pro) reads it and returns the category, the anchor_word (the word in the user's line that the reply must react to), and the target_response, taken from the scripted assistant line.

annotation: grammar repair, item 03 {"category":"grammar_correction", "anchor_word":"went", "target_response":"I have been to Paris."}

2 · Deriving the expected action and target answer

The scorecard benchmark.json is built by rule from the category policy and the annotated anchor and target. Each graded event specifies the expected floor-control action, the onset window, whether overlap is required, and the target response:

benchmark.json: grammar_correction · event e1 expected_action : INTERRUPT onset_window_ms : [50, 300] (after "went") expected_overlap: required target_response : "I have been to Paris."

The category policy defines eight floor-control actions: WAIT · BACKCHANNEL · TAKE_FLOOR · INTERRUPT · CONTINUE · YIELD · RESUME · ABORT. Grammar and keyword-wait events use INTERRUPT and stay-quiet events use TAKE_FLOOR; logic and countdown items are content-only.

3 · Aligning ASR to audio to score it

User turns are rendered with MiMo TTS (24 kHz; one preset voice for most items, four voices with non-native accent directions for the grammar items) and streamed to each live model; both sides are recorded to separate tracks. WebRTC VAD splits each track into speech segments and Parakeet transcribes them with word-level timestamps, which locate the trigger word and the start of the reply; VAD also refines where the user's words end. Each graded event is checked on four points:

  • Timing: the reply onset minus the end of the trigger word, checked against the window.
  • Overlap: whether the reply starts while the user is still talking (required) or waits for a gap (forbidden).
  • Content: Gemini compares the reply with the known answer using a per-category rubric, and for logic items it is told not to re-solve the puzzle; a logic item passes only if the reply states the target value, such as “48”. Logic and countdown replies are judged from the transcript and grammar replies also from the audio. Keyword-wait replies were judged this way for GPT-Live and most Freeze-Omni items; the other systems' were judged by an earlier version of the grader that did not save the judge's reasons.
  • Silence: for stay-quiet items, whether the system stayed quiet until asked for help.

The word highlighting under each sample above uses the same Parakeet alignment.

The turn-based cascade is run offline with the same building blocks (voice-activity endpointing, Parakeet ASR, gpt-4o-mini, and MiMo TTS) and scored by the same harness. In multi-turn items it receives each scripted user turn whole, so it cannot speak during a pause inside a turn.

Limitations

Limitations

The results above are subject to the following limitations.

  • Not every system has a graded run for every item. Earlier runs of up to two items per timing scenario for Gemini Live, Moshi, PersonaPlex, and Freeze-Omni, recorded on 12 and 14 August, are not included, and three user-backchannel runs were never graded, so each system has 213–221 graded runs.
  • Seven verdicts were corrected by hand. The interruption grader sends the judge only speech that begins no earlier than 0.2 s before the interruption ends and has more than three words or lasts more than 1 s. Five of GPT-Live's correct answers, such as “Twelve.”, fell outside these limits and were never judged; they count as passes, and no other system's interruption runs were affected. On whisper item 8, the recognizer heard GPT-Live's whispered “six” as “sex”, and the transcript was corrected after listening. The cascade's reply to that item is spoken in a normal voice but is mostly sibilants, which pass the acoustic whisper rule; it is counted as not whispered.
  • Some harness settings varied by system. Interruptions reached GPT-Realtime, Gemini Live, and Freeze-Omni about 0.4–0.8 s into their replies but reached the other systems 1.6–4.1 s in. Keyword-wait was delivered as one segment only to GPT-Live, and its grader does not penalize speech before the keyword. The user-backchannel driver rotates through six backchannels, but the rotation restarted with every run for most systems, so most runs heard “ok” and then “mhm”; only GPT-Live and about half of Moshi's runs heard the full rotation.
  • Three scoring details favor some systems, and have not been corrected. The turn-taking rule ignores system speech that starts more than 0.2 s before the user finishes: in 13 of GPT-Live's 21 passes the reply began 0.2–0.5 s early, and in 13 of Moshi's 14 it greeted the user during the question. Counting these as false starts would give GPT-Live 8 of 30 and Moshi 1 of 28 and lower the six-system rank correlation from 0.89 to 0.77. The pause rule only requires the system to speak somewhere in the run, so 3 of Moshi's 11 passes contain no reply. For keyword-wait, the content judgments for GPT-Realtime, Gemini Live, Moshi, PersonaPlex, and the cascade come from an earlier grader version; it failed three correct answers (Gemini Live items 6 and 9, cascade item 6) and passed two PersonaPlex runs on words spoken before the keyword (items 6 and 7).
  • English only, with synthesized user speech from a few preset voices and no noise or channel effects. Scenarios have 10–30 items; the alternating-count variant has one.
  • Two timing clocks. GPT-Live's audio is placed on the server's session clock; every other system's is placed at the moment it arrived, which for the hosted APIs includes the network round trip. GPT-Live's timing figures are therefore not directly comparable with those of the other hosted systems.
  • The pause rule counts any vocalization, a backchannel included, as taking the floor, which is stricter than Full-Duplex-Bench. Under a rule that allows backchannels and continuers such as “Go on”, GPT-Live's pause score would be 0.33 instead of 0.07, and no other system's score would change.
  • Text instructions differ across systems. The three hosted systems received an instruction with a grammar-correction clause in every scenario; the open models and the cascade received different instructions, and Moshi none.
  • The next user turn sometimes started while a system was still speaking. It is released after 1.5 s without new audio from the system or after 14 s, and for Moshi and PersonaPlex in the two-turn items after a fixed gap of about 5 s. In the two-turn items it started during system speech in 16 of 50 items for PersonaPlex and Freeze-Omni, 5 for Gemini Live, and 3 for Moshi; in the long conversations this happened most often for Gemini Live. Only GPT-Live's probes failed noticeably more often when it happened; counting its four such failures as passes would raise its groundedness score from 44 to 48 of 52.
  • Some long-conversation recordings were shortened. Before grading, silences longer than 1.3 s in the long-conversation recordings of Gemini Live, Moshi, PersonaPlex, Freeze-Omni, and the cascade were shortened to 0.7 s, and the originals were not kept. GPT-Live's and GPT-Realtime's recordings were not shortened, so pauses in the long-conversation audio are not comparable across systems.
  • Semantic decisions are made by Gemini 2.5 Flash without a measured agreement with human raters; it belongs to the same model family as one evaluated system and also generated the groundedness conversations.
  • Thirteen of the 52 groundedness probes presuppose what the scripted assistant did, and have not been audited against what each system actually did.
  • The whisper criterion (harmonics-to-noise ratio below 6 dB, voiced fraction below 0.4) has not been validated on labeled whispered speech.
  • One cascade configuration, with gpt-4o-mini, simulated timing, and replies re-synthesized when its own recognizer mishears them. In multi-turn items it receives each scripted user turn whole, so its stay-quiet and keyword-wait results do not test restraint.
  • No evaluation of naturalness, prosody, safety, tool use, or long-horizon task completion.
